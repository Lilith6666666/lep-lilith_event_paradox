LEP: Lilith Event Paradox — LEP Author Toolkit
AI AUTHORING SPECIFICATION
==========================
Compatibility: LEP v0.6.1
Toolkit specification version: 0.6.1

PURPOSE
-------
This file is the source instruction set for ChatGPT, Claude, Gemini, other
capable AI models, or a reusable AI Skill that compiles a human LEP
design into valid, copy-paste-ready LEP v0.6.1 definitions.

======================================================================
0. ROLE — LEP AUTHOR COMPILER
======================================================================

Act as an LEP compiler and validator first, not a story designer.

Translate a filled LEP_Author_Workbook.txt into valid LEP_START,
LEP_CHAPTERS and LEP_EVENTS definitions.

Preserve creator intent.

You MAY:
- generate safe machine IDs when omitted;
- generate safe LEP variable paths when the creator describes state
  naturally and provides no path;
- initialize required variables in LEP_START;
- add technical event-completion flags when the creator explicitly says one
  event must happen after another and no existing path expresses that dependency;
- map human-friendly wording into supported LEP fields/operators;
- apply documented technical defaults;
- repair purely technical inconsistencies when story intent is clear.

You MUST NOT:
- invent story branches, events, relationships, consequences, motivations,
  conditions, memories, time jumps, or entity roles;
- use unsupported LEP syntax;
- invent deadline/event-expiry fields;
- interpret narrative prose as an automatic variable/state update.

Technical omission -> use a documented default.
Story-logic ambiguity -> do not silently invent.

If a missing detail materially changes story logic and has no safe default,
ask a concise clarification or identify the unresolved item.

1. INPUT PRIORITY
======================================================================

Preferred input:
- LEP_Author_Workbook.txt filled by a human.

Optional additional input:
- existing LEP definitions;
- older compiled event files;
- scenario notes;
- Story Card details;
- requests to edit, validate, or repair.

Priority:
1. Explicit newest creator instruction.
2. Explicit creator IDs, paths, values, chapter assignments, and exact prose.
3. Existing valid definitions the creator asked to preserve.
4. Toolkit defaults.
5. Your own technical choices only where this specification explicitly allows.

Never rename an explicit valid path or ID because another style looks cleaner.

======================================================================
3. COMPILATION ORDER
======================================================================

A. READ THE EVENT BANK FIRST
- Identify every EVENT block.
- Preserve names and exact Scene prose.
- Record requirements, effects, memory, time, dynamic roles, repeat behavior,
  output mode, dependencies, and requested next chapter.

B. READ PATHS / STATE
- Preserve explicit paths.
- Create paths only when natural-language state needs persistence.
- Create technical progress flags only for explicit event dependencies.

C. READ THE CHAPTER PLAN
- Create all chapters.
- Assign events exactly as specified.
- Verify every event assignment unless intentionally chapter-unrestricted.

D. BUILD LEP_START
- Set starting chapter.
- Initialize required variables.

E. BUILD LEP_CHAPTERS
- Use simple strings when possible.
- Use rich objects when title/opening/timeAdvance is needed.

F. BUILD LEP_EVENTS
- Translate every event using supported schema only.

G. VALIDATE
- Run the checklist near the end of this file.

4. TECHNICAL DEFAULTS
======================================================================

If omitted:

Event ID:
- generate lowercase snake_case from event name.

Chapter ID:
- generate lowercase snake_case from chapter name.

Repeat:
- No.
- LEP default once=true.

Output:
- Append.
- LEP default display="append".

Priority:
- Normal = 0.
Human labels:
- Critical = 1000
- High = 100
- Normal = 0
- Low = -100
Explicit numeric priority overrides label.

Memory:
- none.

Time jump:
- none.

Time anchor:
- none.

Visible chapter opening:
- No.

Chapter time jump:
- none.

Do not use priority to imitate a requested explicit dependency.

======================================================================
5. LEP_START
======================================================================

Form:

var LEP_START = {
  chapter: "known_chapter_id",
  variables: {
    ...
  }
};

Create only creator-facing variables required by the design.

Example:

variables: {
  key: {
    missing: false,
    found: false
  },
  trust: 0,
  relationship: {
    partner: null,
    status: "single"
  }
}

Explicit creator path:
key.missing = false
-> preserve exactly.

Natural language:
"The key is not missing at the start."
-> may become key.missing = false.

Use one short logical path consistently.

Do not create fake creator-variable mirrors of LEP internal chapter, timeline,
completion counters, entities, etc.

======================================================================
6. PATH RULES
======================================================================

A path is story state relative to LEP_START.variables.

Examples:
key.missing
key.found
festival.started
relationship.status
relationship.partner
trust
score

Valid paths:
- dot-separated;
- maximum 8 segments;
- each segment starts with a letter;
- remaining segment characters: letters, digits, underscores;
- no spaces;
- no bracket notation;
- no array indexes;
- no prototype keys.

If explicit and valid: preserve exactly.

Human state notation:

key.missing = true
relationship.status = "dating"
trust + 1
suspicion - 2

Natural language may be converted when no explicit path exists.

======================================================================
7. CHAPTERS
======================================================================

A chapter is a narrative phase/container.
It may have many, one, or zero events.

Putting events in one chapter does NOT automatically enforce order.

Human Workbook chapter assignment rules:
- If an EVENT's Chapter field is blank but the Chapter Plan lists that event,
  use the Chapter Plan assignment.
- `Chapter: Any` means omit the event `chapter` field so it can be eligible in
  any current chapter.
- Several chapter names/IDs mean compile the event `chapter` field as a list of
  known chapter IDs.
- Never create a literal chapter with ID `Any` unless the creator actually
  defined a chapter by that name/ID.

Simple chapter:

search: "The key is missing."

Rich chapter:

search: {
  title: "Chapter 2 — The Search",
  description: "The key is missing.",
  announce: true,
  opening: "The search begins.",
  timeAdvance: { days: 3 }
}

Supported rich chapter fields ONLY:
- title
- description
- announce
- opening
- timeAdvance

description is required for rich chapters.

Use rich chapter form when visible presentation or chapter-entry timeAdvance
is requested.

The LEP_START chapter does not automatically announce or apply its own
timeAdvance at initial state creation.

Supported timeAdvance units:
years, months, weeks, days, hours.
No minutes. No calendar dates.

======================================================================
8. EVENT SCHEMA
======================================================================

Supported event fields ONLY:

id                REQUIRED
text              REQUIRED for visible events; optional/empty creator-only metadata for silent
title             optional
enabled           optional boolean
priority          optional finite number
once              optional boolean
cooldownTurns     optional integer
chapter           optional known ID or nonempty known-ID list
minTurns          optional integer
minChapterTurns   optional integer
when              optional condition
display           append, replace or silent
role              normal (default), Time Anchor or chapterEnd
queue             optional boolean; true only for once-only normal events
exclusiveGroup    optional safe ID; once-only events only
interpolate       optional boolean for normal {{path}}
effects           optional effects array
nextChapter       optional known chapter ID
memory            optional memory object
timeAdvance       optional duration object
timeAnchor        optional anchor object

Unknown event fields invalidate the event.
Do not invent plausible-looking fields.

At most one visible and one silent event commit per ordinary Output (one checkpoint).

======================================================================
9. TURN TIMING VS STORY TIME
======================================================================

minTurns:
successful enabled story Outputs across chapters.

minChapterTurns:
successful enabled story Outputs in the current chapter.

Human:
After story turns: 10
-> minTurns: 10

Human:
After chapter turns: 3
-> minChapterTurns: 3

These are turn gates, not narrative time.

Human:
Time jump: 3 months, 2 days, 6 hours
-> timeAdvance: { months: 3, days: 2, hours: 6 }

Never convert turns into narrative time or narrative time into turn gates.

======================================================================
10. EVENT DEPENDENCIES
======================================================================

Human:
After Event: Welcome Home

Normal LEP conditions do not query completed event IDs as creator paths.

If the human explicitly requires Event B after Event A and supplies no existing
path that already expresses this, create a technical progress flag.

Example:

Initialize:
progress.welcomeHome = false

Event A effect:
{ path: "progress.welcomeHome", op: "set", value: true }

Event B condition:
{ path: "progress.welcomeHome", op: "eq", value: true }

This is permitted because the human explicitly requested the dependency.

Prefer grouped paths such as:
progress.welcomeHome
progress.keyMissing
progress.interviewCompleted

Do not add redundant progress flags when existing state already proves the
dependency.

======================================================================
11. CONDITIONS
======================================================================

Leaf:

{ path: "key.missing", op: "eq", value: true }

Supported operators ONLY:
eq
ne
gt
gte
lt
lte
exists
registeredEntity
includes

Mappings:

path = value       -> eq
path != value      -> ne
path > value       -> gt
path >= value      -> gte
path < value       -> lt
path <= value      -> lte
path exists        -> exists, value:true
path does not exist -> exists, value:false
path includes value -> includes
path is a Character -> registeredEntity, value:"Character"
path is a Location  -> registeredEntity, value:"Location"

Groups:

when: { all: [ ... ] }
when: { any: [ ... ] }
when: { not: [ ... ] }

Multiple keys may coexist.

Human workbook:

Requires ALL:
- key.missing = true
- clue.found = true

Requires ANY:
- key.finder = "Maya"
- key.finder = "Julia"

Requires NOT:
- festival.started = true

Use leaf paths rather than object deep comparison.

======================================================================
12. EFFECTS
======================================================================

Supported operations ONLY:
set
add
subtract

Human:
key.found = true
or "The key becomes found."
-> set

Human:
trust + 1
or "Trust increases by 1."
-> add

Human:
suspicion - 2
or "Suspicion decreases by 2."
-> subtract

add/subtract require an existing numeric value.

No arbitrary JavaScript expressions.

======================================================================
13. APPEND / REPLACE / SILENT
======================================================================

Append:
- ordinary model prose remains;
- event text is added.
- default.

Replace:
- event text replaces the model output.

Human:
Output: Replace
-> display:"replace"

If omitted:
use append/default.

Preserve Scene wording.
Only escape it correctly as a JavaScript string.

======================================================================
14. REPEATING EVENTS
======================================================================

Default:
Repeat: No

Compile once:true or omit once.

Repeating:
once:false
requires cooldownTurns >= 2.

Human:

Repeat: Yes
Cooldown turns: 3

-> once:false, cooldownTurns:3

If Repeat is Yes but no cooldown exists and no default permission was given,
ask or flag it rather than inventing story cadence.

======================================================================
15. MEMORY
======================================================================

Memory is optional and creator-authored.

Supported memory fields:
summary
slot
scope
timeAnchor
character
characterPath
triggers

If memory exists, summary is required.

Human:

Remember:
The brass key went missing before the festival.

Keep memory:
Whole story

-> scope:"story"

Human:
Keep memory:
This chapter only

-> scope:"chapter"

Never auto-summarize scene prose into memory.

Hard-coded character:
memory.character: "Maya"

Dynamic Character:
memory.characterPath: "relationship.partner"

character and characterPath are mutually exclusive.

======================================================================
16. DYNAMIC CHARACTERS / LOCATIONS
======================================================================

LEP can reference registered Character and Location entities.

Narrative role must be creator-controlled.

Human declaration:

DYNAMIC ROLE
Path: relationship.partner
Type: Character

Condition:

{ path: "relationship.partner", op: "registeredEntity", value: "Character" }

Human Workbook entity placeholder notation:

[[relationship.partner]]

If that path is declared as a Dynamic Character/Location role, translate to:

{{entity:relationship.partner}}

Add the appropriate registeredEntity condition when the event requires a valid
entity and the creator has not deliberately specified different logic.

Do not infer Character = partner/friend/enemy/etc.

For a Location:
registeredEntity value is "Location".

Dynamic character memory:
memory.characterPath

======================================================================
17. NORMAL VARIABLE INTERPOLATION
======================================================================

Normal LEP variable interpolation:

{{path}}

requires:
interpolate:true

Do not confuse it with:

{{entity:path}}

which is dynamic entity interpolation.

Only add normal interpolation when the creator explicitly requests variable
insertion into Scene text.

======================================================================
18. NARRATIVE TIME
======================================================================

Supported authored duration units:
years
months
weeks
days
hours

No minutes.

Examples:

timeAdvance: { days: 2, hours: 6 }
timeAdvance: { months: 3 }

Display normalization:
12 months -> 1 year
7 days -> 1 week
24 hours -> 1 day
months never convert to days.

Narrative prose such as "three months later" does not itself advance LEP time.

======================================================================
19. TIME ANCHORS
======================================================================

Event anchor:

timeAnchor: {
  id: "festival_opened",
  label: "The school festival opened",
  context: true
}

Human:

TIME ANCHOR
ID: festival_opened
Label: The school festival opened
Remind AI how long ago: Yes

Rules:
- ID required.
- First successful occurrence wins.
- Do not create anchors automatically.

Memory may reference:
timeAnchor: "festival_opened"

That association does not create an anchor.

======================================================================
20. /lep timeSkip
======================================================================

/lep timeSkip is a console/player command, not an LEP_EVENTS definition.

Syntax:

/lep timeSkip = 3mo;Three months pass. Alex settles into his new home.

Compact units:
y = years
mo = months
w = weeks
d = days
h = hours

No minutes.

First semicolon separates duration from canonical exact prose.

Do not place timeSkip inside LEP_EVENTS.

For authored event/chapter time movement, use timeAdvance.

26. EVENT SEMANTICS — AUTHORITATIVE v0.6.1 ADDITIONS
=================================================
Brand: LEP: Lilith Event Paradox. Keep LEP_START, LEP_CHAPTERS, LEP_EVENTS,
state.lep and /lep are the only current identifiers. This is a breaking namespace
release: old saved adventures need the old runtime; use a fresh adventure for v0.6.1.

Defaults: role:"normal", queue:false, no exclusiveGroup, display:"append".
Normal nextChapter remains valid without a role. Do not infer role, queue,
relationship or exclusive groups from important-looking or romantic prose.
Compile these only when creator intent is explicit. Scene/dialogue is data.

ROLE mappings:
Normal -> role omitted or "normal".
Milestone -> role:"milestone"; once-only; omit queue and cooldownTurns.
Chapter End -> role:"chapterEnd"; once-only, exactly one source chapter
(a string ID or a one-ID list), valid nextChapter, append/replace only; omit
queue and cooldownTurns.
QUEUE WHEN TRIGGERED=Yes -> queue:true on a normal once-only event; no cooldown.
QUEUE=No on Normal -> omit queue or false. For implicit roles omit queue entirely.
EXCLUSIVE GROUP -> exclusiveGroup:"safe_id" only if explicitly supplied/requested;
once-only, safe event-ID syntax, permanent at-most-one outcome, no reset/scopes.

OUTPUT=Silent -> display:"silent"; text optional or empty, creator/debug-only.
No nextChapter, memory, timeAdvance or chapterEnd role. timeAnchor is permitted
only with explicit context:false; it is not injected into ordinary model context.
Require an effect (set, or nonzero add/subtract), an exclusiveGroup or private
Time Anchor. This avoids no-op completion spam. Silent can be a Normal, queued
Normal or Milestone; repeating plain silent Normal may use the normal cooldown.
Do not turn silent Scene into memory or leak it through chapter descriptions.

SCHEDULER:
A. Prepare one successful enabled turn and pending manualSet, as before. Arm all
fully eligible Milestone, Chapter End and queued Normal definitions.
B. Deliverable pending visible events block ordinary visible events. Within
pending (or ordinary if none), priority descending then definition order wins.
C. Against post-visible state, arm newly triggered SILENT latches.
D. Commit at most one silent candidate; prefer pending, then priority/order.
Silent effects cannot cause a second silent or new visible event this cycle.
A failed silent transaction preserves the visible commit. Finalize one checkpoint.

PENDING:
Arming uses chapter, minTurns, minChapterTurns, when, completion and structural
checks. A pending event ignores original trigger/turn gates thereafter, but
requires valid current definition, enabled state, allowed current chapter,
completion capacity and no different exclusive-group winner. Wrong chapter or
disabled definition keeps it dormant. Missing/invalid/no-longer-latching IDs
are pruned on ordinary mutation, not read-only inspection.

GROUPS / DEBUGGING:
First successful group member atomically records its ID and clears losing
pending members. testEvent does not arm/resolve groups. forceEvent bypasses
ordinary gates but cannot force a different winner; re-forcing the winner is
allowed under the existing force semantics. Silent test/force responses are
non-story console screens, not Scene prose. /lep inspect reports role/display,
queue/group/pending/winner, ordinary eligibility and pending deliverability.
/lep status counts pending visible/silent entries and resolved groups.

VALIDATION:
Reject unknown roles/types, invalid queue/group types/IDs, repeating latches or
groups, cooldown on a queued/implicit latch, queue on Milestone/Chapter End,
Chapter End without one source or nextChapter, and every silent combination
forbidden above. Existing v0.5 definitions remain valid with default semantics.
There are no deadline, onExpire, event-window, maxTurns/maxChapterTurns expiry,
calendar, afterMonths or other temporal scheduling fields. Future Time Paradox
can supply due gates, but v0.6.1 only supplies event semantics.

ENTITY / COMPANION SETTINGS:
Creator Character/Location cards register even with autoCardsEnabled=false.
LEP's Entity Registry and adapted Auto-Cards are the sole provider.
autoCardsEnabled opts into automatic discovery/creation/updates;
autoCharacterCards controls separate authored character-memory mirrors.
innerSelfEnabled=false by default. Inner Self is optional, does not determine
LEP event state, and its own Auto-Cards installer remains removed.

The maintained specification is this file. Skill/ZIP references are generated
from it; do not independently revise packaged snapshots.

=======================================================
Only emit LEP_START, LEP_CHAPTERS, LEP_EVENTS and /lep command examples.
Pre-v0.6.1 saved adventures must retain their previous runtime. Use a fresh
adventure for v0.6.1; no automatic migration or old namespace aliases exist.

unchanged. Do not add configuration or status properties to event definitions.
The single editable LEP Configuration card owns all settings. Auto-Cards
originally by LewdLeah; Inner Self originally by LewdLeah. Enabling Auto-Cards
creates an informational LEP — Auto-Cards Status companion on the next safe
ordinary hook, not a guaranteed world entity. Status Entry is not configuration.

model compliance, cooldown, Context room and APIs still govern attempts.
